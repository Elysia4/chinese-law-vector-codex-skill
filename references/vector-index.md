# 向量索引说明

检索默认是纯 BM25（词面匹配）。建好向量索引后，`rank_search.py` 会自动升级为
BM25 + 向量的混合检索。本文档说明它是什么、怎么建、占多少资源、出问题怎么排查。

## 一、它是什么

| 项目 | 值 |
| --- | --- |
| 覆盖范围 | **57309 条**条文（默认只含 `current` 层：现行有效 + 尚未生效；要连历史层一起索引见下） |
| 向量维度 | 1024 |
| 嵌入模型 | `qwen3-embedding:0.6b`（Ollama 官方库，Q8_0 量化，639 MB） |
| 文件 | `references/corpus/vectors.npz`（约 103 MB，float16 存储；全层索引约 155 MB） |
| 元数据 | `references/corpus/vectors.meta.json` |
| 每条向量对应的文本 | 法律名 + 条文号 + 章节 + 正文 |

**每条条文一个向量**，不是每部法律一个。所以语料越大索引越大：307 件法律时是 2.3 万条
（42.8 MB），现在 2476 件、57309 条现行条文是 103 MB。

> ⚠️ 语料每次重建后**必须重建索引**：`vectors.npz` 是按"文件#行号"挂条文的，
> 语料一变行号就位移，旧索引会挂到错误的条文上。`rank_search.py` 检测到覆盖率
> 不足会自动退回纯 BM25 并在"检索方式"里说明，不会给出错误排序。

**关于历史层**：默认只给 `current` 层建索引——问日常问题（默认只搜现行有效）时全部条文都有
向量，最快也最省空间。如果你常查旧案、需要连已废止版本一起做语义检索，用
`python scripts/build_vectors.py --all-layers` 重建（约 85853 条、35 分钟、约 155 MB）。
只覆盖现行层的索引遇到 `--include-repealed` / `--all-layers` 检索时**不会出错**：
`rank_search.py` 会检测到覆盖率不足，自动退回纯 BM25，并在"检索方式"里说明原因。

## 二、为什么分发包里不含它

1. **模型专属**：向量由 `qwen3-embedding:0.6b` 生成。换成 `bge-m3`、`4b` 档或任何其他模型，
   维度或向量空间就变了，旧索引必须整体废弃重建。
2. **体积**：103 MB，比语料本身（35.0 MB）还大两倍多，超过 GitHub 单文件 100 MB 上限。
3. **本机生成更合理**：一次约 25 分钟，语料不变就不用重建。

## 三、怎么建

**前置条件**

```bash
# 1) Ollama 在运行，且拉过嵌入模型
ollama pull qwen3-embedding:0.6b        # 约 639 MB

# 2) numpy（向量读写需要）；Codex 自带的 Python 运行时里已有
pip install numpy
```

⚠️ **生成模型不能当嵌入模型用**——这是最常见的误解。Ollama 里的 Qwen3-4B 这类模型跑
`/api/embed` 会直接报 `This server does not support embeddings`（根因是它的 pooling 类型
为 none，Ollama 不会给它开嵌入接口）。

**先体检，再建索引**

```bash
python scripts/build_vectors.py --check                        # 检查服务与模型是否就绪
python scripts/build_vectors.py --model qwen3-embedding:0.6b   # 全量构建
```

实测：**56984 条用时 21 分钟**（44.8 条/秒，batch 64；含中途被中断后断点续跑的时间）。中途断了直接重跑即可——脚本会检测
已完成条数并从断点续跑；要推倒重来加 `--rebuild`。调试时可只索引一部法律：`--law 刑法`。

## 四、资源占用

| 场景 | 显存 | 说明 |
| --- | --- | --- |
| 默认（Ollama 自动选上下文） | **5.78 GB** | Ollama 按显存给这个 0.6B 模型分了 32768 上下文，纯浪费 |
| 脚本限制 `num_ctx=4096` 后 | **2.37 GB** | 语料最长条文 1873 字符，4096 足够且不截断 |

脚本在每次嵌入请求里带 `num_ctx: 4096`，**只影响这个技能发的请求**，不影响你在别的项目里给
Ollama 设的上下文。

**模型自动卸载**：默认 `keep_alive = 60s`。检索完 60 秒后 Ollama 自动卸载模型并回收 runner
进程，显存回到基线（实测 GPU 占用 4115 MiB → 1851 MiB）。连续追问时模型是热的（单次约
0.2 秒），冷启动加载约 19 秒。

## 五、检索时怎么用它

`rank_search.py` 每次运行会：

1. 检查 `vectors.npz` 是否存在、是否与当前语料匹配（**当前条文覆盖率必须 ≥ 99%**）
2. 探活 Ollama（0.6 秒超时，不拖时间）
3. 两路都可用 → BM25 与向量各出一份排名，用 **RRF（k=60）** 融合
4. 输出首行标明实际用的方式：

```
检索方式：BM25 + 向量（qwen3-embedding:0.6b）
检索方式：仅 BM25（未建向量索引，可用 python scripts/build_vectors.py 建立）
检索方式：仅 BM25（Ollama 未运行——启动 Ollama 后向量检索自动恢复）
检索方式：仅 BM25（索引与语料不匹配，当前条文只有 84% 在索引中…）
```

**任何一路不可用都不会报错**，只是退回纯 BM25。看首行就知道当前状态和检索质量。

## 六、必须重建索引的时机

| 情况 | 要做什么 |
| --- | --- |
| 重建了语料（`build_from_downloads.py`） | **必须重建索引** |
| 换了嵌入模型 | **必须重建**（`--rebuild`），旧索引直接废弃 |
| 只改 `query-expansions.json` | 不用重建（属于检索侧，不进向量） |
| 只改脚本逻辑 | 不用重建 |

**为什么语料变了必须重建**：向量按"文件#行号"挂在条文上。语料更新后条文增删、行号整体位移，
旧向量会挂到错误的条文上——这是静默错误。所以 `rank_search.py` 每次检查覆盖率，低于 99%
就自动退回 BM25 并提示，**不会给出错误的排序**。

## 七、故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `This server does not support embeddings` | 用的是生成模型（Qwen3-4B 等） | 拉专用嵌入模型 `qwen3-embedding:0.6b` |
| 查询向量维度与索引不一致 | 索引与查询用了不同模型 | 用同一模型 `--rebuild` |
| 每次检索都要等约 20 秒 | 模型被卸载后冷启动 | 正常；调大 `CHINA_LAW_KEEP_ALIVE`（如 `10m`）保持热 |
| 显存一直不释放 | 强杀过 ollama，留下孤儿 runner | 用 `ollama stop <模型名>`；排查孤儿 `Get-Process llama-server` |
| 一直显示"未建向量索引" | 索引文件不存在 | 跑 `build_vectors.py` |
| 一直显示"索引与语料不匹配" | 语料重建过但索引没重建 | 重跑 `build_vectors.py` |

## 八、可调参数速查

**环境变量**

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `CHINA_LAW_KEEP_ALIVE` | `60s` | 模型保留时长；`0` = 用完立即卸，`10m` = 保持热 |
| `CHINA_LAW_AUTOSTART_OLLAMA` | `1` | 设为 `0` 则不自动拉起 Ollama，直接退回 BM25 |

**脚本内常量**（`rank_search.py` 顶部）

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `EMBED_NUM_CTX` | 4096 | 嵌入请求的上下文上限（决定 KV 缓存与显存） |
| `RRF_K` | 60 | RRF 融合常数 |
| `VECTOR_CANDIDATES` | 400 | 向量路取前 N 条进入融合 |

**命令行**

| 参数 | 作用 |
| --- | --- |
| `--model` | 指定嵌入模型（必须与建索引时一致） |
| `--batch` | 每批嵌入条数，默认 64；显存紧可以调小 |
| `--check` | 只检查服务与模型就绪，不建索引 |
| `--rebuild` | 忽略已有索引从头重建 |
| `--no-vector` | 检索时临时只用 BM25 |

## 九、容量参考

| 语料规模 | 条文数 | 索引体积 | 建索引耗时 |
| --- | --- | --- | --- |
| 307 件法律（旧语料） | 23126 | 42.8 MB | 约 10 分钟 |
| 2476 件（现行语料，current 层） | 57309 | 约 103 MB | 约 21 分钟 |

耗时与条文数近似线性（约 45 条/秒；RTX 5060 Laptop 8GB + 0.6B 模型实测）。纯 CPU 会慢一个
数量级。
